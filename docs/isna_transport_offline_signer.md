# Nika Business / ИСНА — транспортный подписант на сервере (TEST-only, offline)

## Что уже подтверждено

- KalkanCrypt 2.0.14 на **TEST VPS** успешно проверяет обе ГОСТ-подписи
  недействительного ФНО 000.00, код `0x00000000`.
- SOAP к тестовому ШЭП проходит по IPsec; `SCE010` был на выдуманном
  сервисе, `SCE013` — на `FNO_INTEGRATION` с заведомо неверным `<root/>`.
  Это НЕ подтверждает, что транспортный сертификат зарегистрирован или
  что настоящая ФНО принята.
- Клиент пока выбирает две ЭЦП. Это техническая демонстрация, **не**
  окончательная архитектура подписания налоговой отчётности.

## Что добавлено

`services/isna_transport_certificate.py` — один источник для
контрольного **публичного** сертификата ИС: отпечаток
`ISNA_BIP_REGISTERED_CERT_SHA256` либо файл
`ISNA_BIP_REGISTERED_CERT_PATH`. Если одновременно указаны оба, должны
совпасть. Неисправный файл, неверный SHA-256 или symlink → ошибка, а не
молчаливый переход в режим «не настроено».

`scripts/isna_transport_public_cert.py` — утилита, которую можно
выполнить локально: читает только `.cer/.crt/.pem/.der`,
показывает SHA-256; **не требует присылать .cer в чат**.
Не определяет регистрацию сертификата в ШЭП самостоятельно.

`services/isna_transport_signer_cli.py` — изолированная **ручная**
native Linux `KC_LoadKeyStore + SignWSSE` проба. По ABI KalkanCrypt 2.0
использует `KCST_PKCS12=1`, `KC_XML_EXCL_C14N=0x01000010`, подписывает
только `create_server_signing_sample()` с вымышленным сервисом и
отправителем. Другие SOAP, реальную ФНО, произвольные данные и
сервис `FNO_INTEGRATION` эта команда **вообще не принимает**.

Команда после подписи запускает существующую отдельную проверку
KalkanCrypt на TEST VPS, сверяет открытый сертификат подписи с PIN
зарегистрированной ИС, и только тогда записывает локальную XML-заглушку
с правами 0600. Никаких сетевых вызовов/фискализации или отправки нет.

**Важно:** на дату создания эти native `KC_LoadKeyStore/SignWSSE`
обработчики проверены unit-тестами с заглушками C ABI; **положительный
тест с реальным отдельным транспортным .p12 ещё не выполнен**.
Скорее всего потребуется уточнить результат native `SignWSSE`
и профиль X509Data/WSSE у выданного сертификата. До такого испытания
нельзя считать автоматический транспортный подписант готовым.

## Конфигурация только на TEST VPS

Публичный сертификат, который оператор действительно зарегистрировал
для Nika Business в Smart Bridge, можно сравнить локально:

```bash
cd /var/www/nika-business-test
.venv/bin/python -m scripts.isna_transport_public_cert /secure/IS/registered-public.cer
```

Утилита напечатает `ISNA_BIP_REGISTERED_CERT_SHA256=...`.
После независимого подтверждения в Smart Bridge оператор может записать
этот SHA-256 в **только TEST** `.env` и перезапустить **TEST** сервис.
Либо вместо SHA-256 можно настроить
`ISNA_BIP_REGISTERED_CERT_PATH=/secure/IS/registered-public.cer`.
Не помещать файл в веб-доступный каталог.

На **отдельном Unix-пользователе без прав веб-приложения и без root**
проводится только демонстрационный опыт:

```bash
# Пример ПОСЛЕ создания изолированного аккаунта и приватного каталога.
# Публичный файл и транспортный PKCS12 — РАЗНЫЕ файлы.
# Данный пример НЕ создаёт аккаунт и НЕ загружает закрытые ключи.
cd /var/www/nika-business-test
APP_MODE=test ISNA_KALKAN_LIBRARY=/opt/nika/kalkan/libkalkancryptwr-64.so.2.0.14 \
  ISNA_KALKAN_CA_DIR=/opt/nika/kalkan/trust \
  ISNA_BIP_REGISTERED_CERT_SHA256=<verified-public-64-hex> \
  .venv/bin/python -m services.isna_transport_signer_cli \
  --key-file /secure/nika-is-signer/transport.p12 \
  --output /secure/nika-is-signer/one-off-inert-signed-soap.xml
```

Ключ `transport.p12` должен принадлежать **этому отдельному аккаунту**,
иметь `chmod 0600`, быть недоступным `www-data` и не лежать в
`/var/www`. Пароль вводится интерактивно в терминале, а не в командной
строке, URL, ChatGPT, GitHub, журнале CI или `.env`.
Команда от `root` намеренно запрещена. Результат создаётся 0600.

## Чего ещё НЕТ (не скрывать от пользователя)

1. **Проверка принадлежности ключа Nika в реестре ШЭП/Smart Bridge.**
   Локальный SHA-256 доказывает только соответствие публичному файлу,
   выбранному оператором; нужен ответ от уполномоченной системы.
2. Безопасный **автоматический** сервис транспортной подписи по
   Unix-socket/SSH/HSM с отдельными полномочиями, аудитом и
   исключением ключа из Flask/Gunicorn. Операторский локальный CLI
   нельзя вызывать из интернет-доступного API.
3. Полная схема JSON `fnoDto` и ФЛК для формы 910.00 за 2026 год;
   `declareRequestResponseTypes.xsd` описывает только оболочку обмена.
4. Проверка полномочий налогоплательщика, идемпотентность, отслеживание
   статуса ФНО, защищённый аудит и явное разрешение на TEST POST.
5. Конфигурация **PROD на другом VPS**, его SDK, системные сертификаты
   и секреты пока не меняются.

Официальная документация КГД по JSON ФНО:
https://www.gov.kz/org/kgd/press/article/details/233841
(ссылка в вопросе №3 на каталог документов в Google Drive).
