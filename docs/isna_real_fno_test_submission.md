# Nika Business / ИСНА — реальная ФНО на TEST ШЭП

## Что изменилось

`services/isna_real_fno_submission.py` — отдельный операторский CLI
для **настоящей** (не тестовой `000.00` и не `<root/>`)
подписанной формы 200.00 или 910.00. Он отправляет её через закрытый
IPsec на зафиксированный TEST ШЭП с serviceId=FNO_INTEGRATION,
анализирует ответ и сохраняет журнал попытки.

**Это не отправка на PROD.** Кнопка в Android не включается:
у публичного мобильного API нет права автоматически отправлять ФНО.

## Требования

1. Взять **официальный актуальный JSON fnoDto** для нужной формы и
   налогового периода и проверить его на полноту. Генератор налоговой формы
   в Nika пока не существует; нельзя подставлять догадки вместо полей.
   КГД опубликовал ссылку на форматы JSON:
   https://www.gov.kz/org/kgd-pavlodar/press/article/details/235483?lang=ru
2. Подготовить реальный XML
   `<root><data>{"code":"910.00","fnoDto":{...}}</data><ds:Signature>...</ds:Signature></root>`.
   Внутренняя XMLDSig должна быть сделана уполномоченным
   налогоплательщиком с его ЭЦП. Демонстрационная подпись
   или XML без действительной криптографической подписи запрещены.
3. Проверить на Smart Bridge назначенный senderId, разрешение
   FNO_INTEGRATION и **зарегистрированный публичный сертификат
   транспортной подписи самой ИС**. Локальный SHA-256 не доказывает
   регистрацию сертификата на шлюзе.
4. Настроить на TEST VPS KalkanCrypt и **отдельную** учётную запись
   транспортного подписанта: не root, не www-data. Транспортный .p12,
   подписанный XML и приватный каталог журнала находятся вне /var/www.
   Файлы принадлежат подписанту и имеют chmod 0600, журнал — chmod 0700.
   P12 и пароли не передавать в чат, GitHub и веб-приложение.
5. Только на TEST: `APP_MODE=test`,
   `ISNA_BIP_URL=http://195.12.113.7/bip-sync-wss-gost/`,
   зарегистрированный `ISNA_BIP_SENDER_ID`,
   `ISNA_KALKAN_LIBRARY`, `ISNA_KALKAN_CA_DIR`,
   `ISNA_BIP_REGISTERED_CERT_SHA256` (или путь публичного .cer).
   **Включить вручную:** `ISNA_FNO_REAL_TEST_POST_ENABLED=1`.
   Без этой переменной реальная отправка закрыта.

## Команда одной реальной отправки (TEST)

Убедиться в содержимом подписанной ФНО и вычислить SHA-256 файла:

`sha256sum /secure/nika-isna-signer/fno-signed.xml`

Также определить SHA-256 **DER-сертификата налогоплательщика,
встроенного в его внутреннюю XMLDSig**. Он не равен хешу XML и
не обязательно совпадает с транспортным .cer.

Затем под выделенной учётной записью на TEST VPS:

```bash
cd /var/www/nika-business-test
.venv/bin/python -m services.isna_real_fno_submission \
  --signed-fno /secure/nika-isna-signer/fno-signed.xml \
  --transport-key /secure/nika-isna-signer/transport.p12 \
  --journal-dir /secure/nika-isna-signer/journal \
  --expected-code 910.00 \
  --confirm-payload-sha256 <SHA256_ПОДПИСАННОГО_XML> \
  --taxpayer-cert-sha256 <SHA256_X509_НАЛОГОПЛАТЕЛЬЩИКА> \
  --confirm SEND_REAL_FNO_TO_TEST_SHEP
```

Пароль транспортного .p12 вводится **интерактивно**, не через командную
строку и не в переменной окружения. Генератор не использует чужую ЭЦП
без явных полномочий владельца ФНО.

## Что делает команда

1. Проверяет SHA-256 XML, выбранный код ФНО, наличие полной внутренней
   XMLDSig и отпечаток сертификата налогоплательщика.
2. Независимая криптопроверка внутренней ГОСТ-подписи на KalkanCrypt TEST VPS.
3. Формирует корректный SyncChannel v10 SOAP с
   `requestData/data xsi:type="xs:string"` (не вкладывает XML узлом).
4. С помощью отдельного транспортного .p12 подписывает SOAP Body в WSSE
   и независимо проверяет ГОСТ-подпись, исходный XML и закреплённый
   публичный сертификат.
5. Создаёт эксклюзивную запись в защищённом журнале **до** сетевого POST.
6. Делает ровно **один** HTTP POST через IPsec на
   `195.12.113.7:80/bip-sync-wss-gost/`, возвращает
   HTTP-статус, SOAP Fault/код ШЭП и бизнес-ответ.
7. Отмечает `service-reported-success` только при HTTP 200,
   SOAP responseInfo/status/code=OK **и** JSON success=true.
   Это ещё не окончательное подтверждение о принятии ФНО
   налоговым органом.

При таймауте состояние в журнале останется `attempted`,
повтор запрещён до ручной сверки по messageId, fnoId,
сессии ШЭП и `FNO_INTEGRATION_STATUS`/кабинету ИСНА.
**Никаких автоматических ретраев.**

## Что ещё должно подтвердиться на реальном сертификате

- В предыдущих тестах Linux native `SignWSSE` был проверен unit-тестами
  с имитацией C ABI, но **не положительным вызовом отдельного
  настоящего P12**. Если он возвращает другой профиль XMLDSig/WSSE,
  CLI корректно откажет в отправке — проверки обходить нельзя.
- Предыдущий `HTTP 500 SCE013` означает, что тестовый шлюз вернул ошибку
  целевого сервиса на фиктивные данные. Это **не** успешная ФНО.
- Nika пока не формирует реальный заполненный fnoDto, не проводит ФЛК
  и не предоставляет интерфейс Android для боевой отправки.
  Для запуска нужен уже подписанный правильный XML ФНО.
